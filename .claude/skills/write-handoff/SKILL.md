# 引き継ぎを書く

結果・決定・ジョブ・次の作業を変えたタスクの完了を報告する前と、長時間・高コストのジョブを投げる前に使います。
セッションがいつ終わるかは分からず、チャットでの報告は次のセッションにも、もう一方のエージェントにも残りません。
目標はひとつ、**新しいセッションが `STATE.md` を入口に、ファイルだけで再開できること**です。

## 手順

1. **`STATE.md` の変わった節をすべて更新する。**
   - 最終更新(日時 + 誰が)、段階、現在の焦点
   - 実行中・待ちのジョブ: Job ID、**どう確認するか、結果をどこに書くか**。
     `experiments/JOBS.md` に行があるか確かめる。「確認方法」が無いジョブは、
     次のセッションが放置するか二重に走らせる。終わったジョブは JOBS.md に結果を追記し、STATE.md の行を消す
   - 直近の決定事項: 決めたことと**理由**(今の段階のものだけ)
   - 未解決の問い: 次のセッションが考えるべきこと
   - 次の作業: 優先度を付け直し、終わった行は消す
   - ブランチやコミットの状態は書かない(`git status` と `git log` で分かり、書くとすぐ古くなる)

2. **今回の成果が正しいファイルに入っているか確かめる。**
   正となる場所は `AGENTS.md` の Single Source of Truth の表にある(表はそこだけに置き、ここには写さない)。
   チャットにしか無いものがあれば、いま書く。特に次の4つ。
   - 実験の結果 → その実験の `summary.md`(答え・主な数値と出所・本実行)と `README.md`(日付つきの記録)、`experiments/EXP_SUMMARY.md` の行
   - 撤回・訂正・置き換え → `experiments/README.md` の手順(`summary.md`・索引・`docs/guardrails.md` を同じコミットで)
   - 繰り返さない失敗 → `docs/guardrails.md`
   - 新しい案・却下した案 → `docs/ideas.md`

3. **経緯を残す価値があれば、`docs/` に研究ログを書く**(雛形は `docs/templates/research-log.md`)。
   分岐の多い調査、方針転換、長いデバッグのとき。恒久的な判断は意思決定記録にする。

4. **構造の検査を通し、`STATE.md` をコミットする。**
   `docker compose exec research-template uv run pytest tests/test_repo_structure.py -q` が通るまで直す
   (常に読む文書の長さ、索引と実験ディレクトリ、`summary.md` の状態の語)。長すぎる文書は、古い決定を
   研究ログ・意思決定記録へ、実験の詳細をその実験の `summary.md` へ移して縮める。
   そのうえで `STATE.md` を作業ブランチにコミットする。

## 確認

`STATE.md` を**まっさらなセッションのつもりで読み直す。**
再開に要るもので欠けているものはないか。あれば足す。

特に確認すること。

- 実行中のジョブに「確認方法」と「結果の記録先」が書いてあるか
- 今回触れた実験の `summary.md` の状態と `experiments/EXP_SUMMARY.md` の状態欄が同じ語か
- 撤回が `summary.md`・索引・`docs/guardrails.md` に反映されているか
- 次の作業の P0 が、いま本当に最優先か
